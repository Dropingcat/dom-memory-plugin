## 1. Относительно главной задачи

### Главная задача
> **Разработка плагина DOM** — Плагин ведения памяти проекта: помогает агенту помнить, с чего начат проект и что он делает сейчас.

### Что это означает на практике

Плагин DOM — это **прослойка между агентом и проектом**:
- Он **запоминает** решения, код, данные (claims)
- Он **показывает контекст** в каждом промпте (brief)
- Он **направляет** агента к ближайшей задаче (step lock + skill queue)

### Что хорошо (относительно главной задачи)

| Аспект | Состояние | Почему хорошо |
|--------|-----------|---------------|
| **Память** (claims) | Все решения зафиксированы | База 609 claims, chain OK |
| **Контекст в промпте** (brief) | Переработан — шум убран, hierarchy добавлена | Агент видит {ЦЕЛЬ → ТЕКУЩАЯ ЗАДАЧА → ДАЛЕЕ} за 2 секунды |
| **Step lock** | CURRENT: строка + plan_version парсятся | skill queue может работать |
| **Promptizer** | Fallback + расширенные маркеры | Находит любой claim, даже без идеальных маркеров |
| **Plan identity** | P1 fix: `base_revision` inject | Больше не плодятся мусорные plan_task_id |

### Что плохо (относительно главной задачи)

| Аспект | Состояние | Почему плохо |
|--------|-----------|---------------|
| **Модель не пишет claims** | Нет автоматического механизма | Память не наполняется. Brief видит claims только если их написал разработчик вручную |
| **Skill queue мёртв** | Нет CAP на П1, нет E2E-теста | Селектор skills работает (pipeline), но очередь не доставляется в промпт |
| **τ-gate не проверен** | Нет live-сессии | Неизвестно, переиздаётся ли блок или idle |
| **План фрагментирован** | Hotfix перезатёр П1, 29→18 items | Потеряна часть иерархии |
| **Нет loop** | Нет цикла "сделал → записал → увидел → сделал" | Модель работает вслепую |

## 3. Относительно шагов (micro-level)

### Как должно работать (идеал)

```
Шаг N:    Модель пишет dom_claim({text: "Сейчас: читаю файл X...", keywords:["now"]})
          ↓
Шаг N+1:  Brief показывает CURRENT MEANING: "Сейчас: читаю файл X..."
          ↓
Шаг N+1:  promptizer находит claim → заполняет step context
          ↓
Шаг N+1:  skill queue получает context → inject skills
          ↓
Шаг N+1:  Модель работает → пишет dom_claim({text: "Сейчас: анализирую...", keywords:["now"]})
          ↓
          ...цикл...
```

### Текущее состояние шагов

| Шаг | Статус | Почему |
|-----|--------|--------|
| Шаг 1: "Сейчас: завершаем аудит..." | ✅ Записан в П1 | Ручной dom_claim |
| Шаг 2: модель пишет claim | ❌ Не написан | Нет инструкции в brief |
| promptizer находит шаг 1 | ✅ Будет найден | markers + fallback |
| promptizer находит шаг 2 | ❌ Нечего находить | claim не написан |
| skill queue inject | ❌ Нет CAP | П1 без accept |

### Почему шаги не пишутся автоматически

**Три причины:**

1. **Brief не говорит модели "напиши claim"**  
   В блоке `── ТЕКУЩАЯ ЗАДАЧА ──` нет строки вида:
   ```
   После выполнения шага напиши:
   dom_claim({plan_task: "П1", type: "text",
     text: "Сейчас: <что сделано и что дальше>",
     keywords: ["now"]})
   ```

2. **Нет обратной связи**  
   Модель не видит, что её claims читаются. Если бы brief показывал:
   ```
   Последний записанный шаг: "Сейчас: завершаем аудит..."
   ```
   модель понимала бы, что механизм работает.

3. **Нет шаблона в mini-prompt**  
   `promptizer.py` имеет `mini_prompt()` для каждого поля, но его никто не показывает модели.

## 4. Сборка реализации: что делать, почему хорошо/плохо

### Этап 1: Замкнуть loop (P4)

**Что делать:**
Добавить в brief инструкцию писать claim после каждого шага, в секцию `── ТЕКУЩАЯ ЗАДАЧА ──`:

```
  После выполнения → запиши dom_claim({plan_task: "П1",
    type: "text", text: "Сейчас: <итог>",
    keywords: ["now"]})
```

**Хорошо:** Модель получает шаблон, цепочка замыкается за 1コミット.
**Плохо:** Добавляет ~200 символов в brief. Если модель не следует инструкции — бесполезно.

### Этап 2: CAP + accept (P4.1)

**Что делать:**
Добавить `accept` свойство на П1 через `plan_ingest` с `contexts`:
```python
contexts={"П1": "...", "accept": [{"provider": "sqlite"}, {"provider": "testing"}]}
```

**Хорошо:** Skill queue запускается, producer отбирает skills по CAP.
**Плохо:** Нужно знать, какие skills нужны для П1. Без E2E-теста не проверить.

### Этап 3: E2E live test (P4.2)

**Что делать:**
Запустить `opencode run --agent dom-router` и проверить:
1. `dom.skill-queue` есть в system blocks?
2. Токены skills до/после — 70K → ~2K?

**Хорошо:** Единственный способ проверить, что цепочка реально работает.
**Плохо:** Требует живой сессии OpenCode, не自动化 в CI.

### Этап 4: Наполнить claims для П1.1–П4.6 (P4.3)

**Что делать:**
Для каждого подпункта П1.1–П4.6 написать `dom_claim` с `keywords: ["now"]`, описывающий текущий шаг.

**Хорошо:** promptizer находит контекст для каждого микрошага.
**Плохо:** Ручная работа. Claims устаревают если план меняется.

### Этап 5: Автоматический claim от модели (P4.4)

**Что делать:**
Добавить в `promptizer.py` `mini_prompt()` в brief — инструкция для модели:

```
#prompt: запиши dom_claim с keywords:["now"] после каждого tool call
```

**Хорошо:** Модель сама ведёт лог шагов.
**Плохо:** Модель может не следовать инструкции. Нужен fallback.
