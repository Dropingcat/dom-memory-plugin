# Концепция: DOM как хранилище утверждений, цикл агента и канбан с ТРИЗ

**Статус:** черновик для обсуждения. Не внесено в DOM. Не утверждено.
**Дата:** 2026-11-23

---

## 1. Разделение хранилищ

- **DOM** — хранилище утверждений и веток поиска: claims, решения, планы, их происхождение и связи. Утверждение короткое, проверяемое, с источником.
- **БД (заметки/артефакты)** — оцифрованные заметки, полные тексты, таблицы, файлы. Развёрнутые материалы, на которые ссылаются claims.

Граница: DOM не хранит развёрнутые тексты, БД не хранит решения как проверяемые утверждения.

## 2. Цикл агента

Агент работает внутри цикла «DOM ↔ БД ↔ агент». Базовый агентский промт (хост: OpenCode, Hermes, Claude) содержит правило: перед любым решением или действием агент сверяется с DOM и БД.

Инъекция DOM (план и claims) — отдельный цикл: промт → DOM → инъекция в контекст → вопрос/задача агенту. Инъекция запускает агента на расширение, аналитику или сравнение с базлайном.

### 2.1. Правило цепи (гейт)

Перед решением агент обязан пройти одну из ветвей:

1. **Сверка:** прочитать DOM и БД по теме задачи.
2. Если сверка не даёт ответа — **поиск / ресерч / дистилляция** по первой задаче.
3. Результат — **внесение claim** в DOM (с источником или пометкой «интерпретация»).
4. **Повторная сверка** с обновлёнными данными.
5. Если и после этого не хватает — **консультация с пользователем**. Ответ пользователя вносится в DOM и БД, затем цикл повторяется с п.1.

Действие без прохождения ветви — нарушение. Цель: агент не может перейти к решению, минуя сверку.

### 2.2. Глубина контекста

Если агент уходит в глубину (цикл не сходится, ветви плодятся):

- запросить у пользователя **рамки** (что входит, что нет);
- принять пользователя решение о продолжении исследования или о **минимальном решении по реализации**;
- зафиксировать решение в DOM.

### 2.3. Открытый вопрос

Гейт в промте — слабое средство: агент может его обойти. Нужен механический контроль (hook или runtime-проверка, что сверка с DOM была перед записью решения). Это предмет отдельного обсуждения и не решено здесь.

## 3. Канбан и техкарты (модуль)

Связка: **план → задача → техкарта → исполнение**.

- **План** — ветви claims в DOM (план П5–П13 как пример).
- **Задача** — пункт плана с критерием готовности.
- **Техкарта** — пошаговое описание исполнения задачи, сгенерированное после анализа.

### 3.1. ТРИЗ в лоб

Каждая задача разбивается ТРИЗ через чек-листы. Неоднозначности передаются аналитикам через чек-листы.

Для каждого варианта отдельно и независимо:

- почему он лучше;
- почему он хуже;
- почему он плохо;
- почему он хорошо.

Так снимаются однобокие оценки. Это принцип независимости: аналитики не видят выводов друг друга до сведения.

### 3.2. Сведение

Полученное через модуль планирования и дистилляции:

1. выявляется суть специфики задачи;
2. строится базлайн относительно материнской задачи;
3. текущий вариант сравнивается с claims DOM;
4. план обновляется;
5. выпускаются техкарты без двойственностей с критерием завершённости блока.

### 3.3. Аудит и штрафы (предложение)

- После крэш-аудита блока найденные баги дают **штрафные очки**.
- Штрафы уменьшают **допустимое число токенов на действия** в следующем цикле.
- Снижение квоты явно заявляется агенту и пользователю.

Открытые вопросы: как считать серьёзность бага; кто вычисляет штраф (детерминированный скрипт или аналитик); как не наказывать за ошибки, вызванные неполным контекстом.

## 4. Директор как роутер (эксперимент)

Проверено на Windows 2026-11-23: Director поднимает плейбук, фильтрует инструменты (dom_describe, dom_claim, dom_find), работает через HTTP endpoint.

Что Director **умеет**: выбор набора инструментов по плейбуку, логирование вызовов, единый endpoint.

Что Director **не умеет** (по документации и по исходникам): не принимает решение по задаче, не реализует гейт «сверка перед решением», не multi-agent. Значит как «роутер задач» он даёт ограниченную пользу: переключение наборов инструментов.

Вывод для эксперимента: тестировать как транспорт и фильтр инструментов. Гейт и цикл — отдельный слой (hook/runtime харнесса). Пустой тратой ресурсов будет считать Director роутером логики задач.

## 5. Соответствие уже принятым решениям

- Маршрутизация скилов/агентов/моделей — не DOM (`положения.md` §5.2 п.8, §5.3, U-013; claim `5140706e`). Гейт цикла — тоже не DOM: он в хосте/харнессе, DOM даёт только данные.
- DOM не выполняет выбор инструмента; он хранит факт выбора, если это проектный факт.
- Ядро DOM работает без Director (`положения.md` §5.2 п.5).

## 6. Наблюдаемость: слепок собранного промта

Точка слепка — хук OpenCode V2 `context`. Он получает `system`, `messages`, `tools`, `options` непосредственно перед отправкой модели. Это семантически собранный промт, а не сырое тело HTTP-запроса провайдера.

Снимок:

- делается после DOM-инъекции, в том же хуке;
- сохраняет `system` как массив блоков (с `metadata.experimental.instructions`, если есть), `messages` с ролями и текстовыми частями, имена и схемы `tools`, `options`, `model`, `agent`, `sessionID`;
- помечает DOM-блоки (`origin: "dom"`, `source`, `claim_ids`), чтобы монитор отделял вклад DOM от остального промта;
- хранится в `.dom-memory/observability/prompts/<session>/<ts>-<hash>.json`, gitignored, с ограничением размера и retention;
- не пишет полные бинарные вложения, только ссылки и текстовые части.

Хуки выполняются в порядке плагинов, поэтому DOM должен загружаться последним. Если другой плагин зарегистрирован после DOM, его изменения в снимок не попадут; это надо явно писать в мониторе.

Рядом пишется журнал хуков `.dom-memory/observability/hooks-YYYY-MM-DD.jsonl`: `hook`, `phase`, `session_id`, `duration_ms`, `status`, `source`, `extracted`, `injected` (chars, sha256, preview), `context` (system size до/после), `gate`, `error`.

## 7. Монитор

В OpenCode V2 есть экспериментальная GUI-часть плагина с `Panel` в `region: "side"`. Нативная боковая панель возможна, но API экспериментальный и требует сборки Solid/Vite. Поэтому:

- **0.2.6:** локальная read-only веб-панель — быстрый, переносимый и тестируемый вариант; открывается в браузере.
- **0.3.1:** нативный Panel-адаптер в OpenCode Desktop поверх того же JSON API.

Вкладки: «Хуки и инжекции», «DOM claims», «План», «Здоровье». Только GET, только `127.0.0.1`, случайный token в URL, без записи. Полные тексты claims не дублируются в журнале — только preview и ссылка на claim id.

## 8. Единый интерфейс записи

| Вариант | Суть | Оценка |
|---|---|---|
| A. Общий `Service` | hooks и MCP вызывают один admission-слой; `origin` и `session` пишутся в каждый claim | рекомендуется как инвариант |
| B. Все через MCP | hooks становятся MCP-клиентами | прототип для `plan_ingest`, не для каждого prompt |
| C. Локальный admission-демон | один писатель через IPC | позже, если A не хватит |
| D. Hooks только читают | пишет агент через MCP | политика для агентских claims |

Рекомендация: A как семантическая граница, B — прототип для `plan_ingest`, D — политика для агентских claims. Хуковые записи остаются нативными доверенными, но маркируются `origin=hook` и логируются.

## 9. Принятые решения

- **D-015:** гейт — 0.3.0; правило `dom_find` + `basis` из прочитанных в этой сессии id.
- **D-016:** хуковые записи нативные доверенные, но отслеживаемые: `origin=hook`, session, timing, результат.
- **D-017:** Director 1.1.1, опционально, не в критическом пути.
- **D-018:** единый Python-resolver пути памяти; `DOM_DIRECTORY` приоритетнее `CLAUDE_PROJECT_DIR`/`OPENCODE_PROJECT_DIR`; все entry points используют его; `db_path` realpath пишется в health.
- **D-019:** доверенная сессия только из launch-trusted источника; аргументы MCP не задают `origin`/`session_source`; гейт 0.3.0 читает DB `read_receipts`, а не JSONL.
- **D-020:** split: 0.2.6 — только наблюдаемость (resolver, snapshot, journal, monitor); 0.3.0 — доверенная запись и гейт (`WriteContext`, `claim_sessions`, `read_receipts`, Panel 0.3.1). В 0.2.6 нет изменений схемы claims.

## 10. Открытые вопросы

1. Формула штрафов и бюджета токенов.
2. Что записывать в DOM из ТРИЗ-анализа: только итоговые техкарты или все ветви «за/против».
3. Нужен ли отдельный аналитик на каждую ветвь ТРИЗ.
4. Формат retention для снимков промта (дни или количество).
5. Нативная панель: делать в 0.3.1 или сразу вместо веб-панели.
